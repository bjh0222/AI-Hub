## 0. 结论速览（先看这一页）

| # | 议题 | 决策 | 一句话理由 |
|---|---|---|---|
| 1 | 版本与路由 | **Next.js 16.4.x + App Router + TS + Tailwind**；不启用 Cache Components，先关掉预热式缓存优化 | 单页静态导航站没有个性化服务端数据，缓存模型越简单越不出错 |
| 2 | 后端/数据库 | **确认：不需要数据库、不需要独立后端服务**；但需要 **1 个 Node 进程内的 2 个 Route Handler**（登录/登出） | 密码校验 + `httpOnly` Cookie 只能服务端写；会话用 HMAC 无状态，不需要存储 |
| 3 | 访问保护 | **b 案（根 layout，Node Runtime，`node:crypto` HMAC）+ 不写 Proxy/中间件** | 避开 Edge/Node 差异；Next 官方明确建议"除非别无办法，不要用 middleware" |
| 4 | 持久化 | **localStorage 足够**；单一根键 `aihub:v1:state` + 版本号 + 白名单校验 | 单浏览器自用，数据量小于 5 KB，上数据库是纯负债 |
| 5 | 一键多开 | **TabList（同手势同步开 1 个 + 渲染可点链接列表）+ 复制全部链接兜底 + 最后给 Bookmarklet【待核实】** | 弹窗拦截不可靠，方案不能建立在"能开 6 个标签"的假设上 |
| 6 | 测试 | Vitest 单测（storage 迁移、限流、HMAC）+ **不默认装 Playwright**，登录链路走 5 步手工清单 | 单人项目给 UI 自动化装依赖，利息比收益高 |
| 7 | 部署 | 本地 `next dev` → 局域网 `next start -H 0.0.0.0` + 防火墙入站规则 → Vercel / Windows 常驻（pm2 / NSSM）三选一 | `next dev` 与 `next start` 默认已绑定 `0.0.0.0`，**不需要改代码** |
| 8 | 风险 | 入口 URL 集中到 `data/platforms.ts` 一处；cookie 泄露/弱密码/CSRF/XSS 各有明确缓解；**暂不建议**清单 7 项 | 这个项目最大的风险不是被黑，是"半年后没人知道官方地址变了" |

**需要你拍板的 3 件事**（我给成本，你选）：

1. 局域网是否需要 HTTPS。不用 HTTPS → `Secure` 必须关，会话令牌在局域网内**明文传输**；用 Tailscale / Caddy 内网证书 → 多花约半天配置。**我的建议：若家里 Wi-Fi 有访客或智能设备，花这半天。**
2. 一键多开是"尽力开"还是"保证全部可达"。前者省事但可能只开出 1 个；后者多一个列表页交互，但 100% 可达。**我的建议：后者作为默认。**
3. 是否接受"改密码 = 重新登录所有设备"。接受 → 实现极简；不接受 → 需要一会话表（引入数据库），我不建议。

## 1. Next.js 版本与 App Router 选择

### 1.1 决策

| 项 | 决策 | 取舍（代价） |
|---|---|---|
| Next.js | **16.4.x（当前 stable，2026-10-06 发布）**，用 `create-next-app` 起 | 16.x 已把 `middleware.ts` 更名为 `proxy.ts`（v16.0.0 起 `middleware` 弃用），网上 95% 的教程仍是 v14/v15 写法，抄代码时要主动鉴别 |
| Router | **App Router（`app/`）** | 如果你以后想 `output: 'export'` 纯静态托管，App Router 的静态导出确实支持，但访问保护会失效（见 §2.6），这一点要提前知道 |
| 语言 | TypeScript `strict: true` | 单人项目改类型成本几乎为零，收益是重构时不炸 |
| 样式 | Tailwind CSS | 6 个卡片 + 搜索框的量级，手写 CSS 也行；Tailwind 的价值在"不用起名" |
| React | 随 Next 16.4 自带的 React 19.3 | 无自定义需求，不要单独锁 React 版本 |
| 包管理 | 用你机器上已装的 npm 11 / Node 24（实测：Node v24.21.0、npm 11.19.0） | 不要为这个项目再引入 pnpm workspace |

**版本踩坑提醒（真实存在，不是理论）：** Next 16.4 起 `create-next-app` 默认开 **Cache Components**（`'use cache'` 那套新缓存模型）。它对"静态导航站"没有任何收益，反而会因为 `cookies()` 在 layout 里被调用而制造"prerender 被阻塞"的构建报错。**决策：显式不开 `cacheComponents`**；如果脚手架默认开了，在 `next.config.ts` 里关掉并确认构建通过。

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  // 单页导航站：不要 Cache Components，缓存语义越少越好
  // cacheComponents: false,   // 若脚手架默认开启，显式关闭
  output: process.env.BUILD_STANDALONE === '1' ? 'standalone' : undefined,
  experimental: {
    serverActions: {
      // 仅当部署在反向代理后面、Host 与外部域名不一致时才需要（见 §2.6 CSRF）
      allowedOrigins: process.env.ALLOWED_ORIGINS?.split(',').filter(Boolean),
    },
  },
}

export default nextConfig
```

### 1.2 升级路径（避免以后被版本绑架）

- 现在锁 `16.4.x`，用 `package-lock.json` 提交入库。
- 每季度跑一次 `npx next upgrade --revision latest`（Next 16.1+ 提供 `next upgrade` 命令），**在独立分支上做**，构建与登录链路跑一遍手工清单（§6.2）再合。
- 触发"必须升级"的信号：出现影响本项目的安全公告、或 Node 版本 EOL。其余时间不追新。
- 风险提示：Next 17 会把 Cache Components 变成默认模型，届时升级需要读迁移指南。**这是已知的未来本金，不是现在的利息**，写进 §11 债项台账。

## 2. 是否需要后端 / 数据库

### 2.1 你的判断：部分成立，需要精确反驳一半

> 你的判断："不需要后端/数据库"。

- **不需要数据库：确认成立。** 收藏 / 最近使用是单浏览器数据，来源就是你自己的点击行为；上 SQLite/Postgres 只会引入备份、迁移、连接、崩溃恢复四件事。
- **"完全不需要服务端代码"：不成立。** 原因只有一个，但无法绕过：**会话令牌必须放在 `httpOnly` Cookie 里**，而 `httpOnly` Cookie 只能由服务端响应头写入（`Set-Cookie`）。客户端 JS 写不了 `httpOnly`，这是浏览器的定义。
  - 如果为了"零后端"把令牌放 `localStorage`：任何一次 XSS（哪怕是第三方依赖引入的）就能直接读走会话；而且校验逻辑（HMAC 密钥）会进客户端 bundle，等于把锁和钥匙一起给了攻击者。**这是我不接受的方案，属于我行使否决权的那一类（安全底线）。**
  - 因此最小服务端面 = **1 个 Node 进程（`next start` 本身）+ 2 个 Route Handler**（`POST /api/auth/login`、`POST /api/auth/logout`）+ 根 layout 里一次 Cookie 校验。没有额外进程、没有额外端口、没有额外依赖。

### 2.2 两档方案对比（业务约束先行）

**业务约束**：目标 = 单人可用的快捷入口｜截止 = 无硬性｜预算 = 一个晚上到两个晚上｜不可动的承诺 = 只做跳转、不接 API、不爬取、可本地跑

|                | A 档：快（推荐） | B 档：对（多设备/多用户） |
|---|---|---|
| 方案要点 | 无数据库；密码哈希走环境变量；HMAC 无状态会话 Cookie；收藏/最近使用在 localStorage | 引入 SQLite（`better-sqlite3`）或托管 Postgres，存用户表 + 收藏表 + 最近使用表 |
| 上线时间 | **0.5 天** | +2～3 天（含 schema、迁移脚本、备份策略） |
| 一次性成本 | 近乎为零 | 2～3 人日 |
| 每月运维成本 | 0（同一进程，无额外常驻） | 备份校验、磁盘/连接监控、【待核实】若用托管 Postgres 需按其公开价目核对 |
| 引入的技术债 | 换设备/换浏览器收藏不同步（利息：手动导出一次，5 分钟） | 多一个数据面要备份与恢复演练（利息：每月约 1 小时维护） |
| 失败模式 | 浏览器清站点数据 → 收藏丢失（用 JSON 导出兜底） | 数据库文件损坏 / 迁移失败 → 站点打不开 |
| 退出/迁移路径 | 收藏数据是 JSON，导出后写个脚本即可入库 | 反向迁移同样简单（导出 SQL 为 JSON） |
| **推荐** | **A 档**。在"单人自用、数据量 < 5 KB、只在本机和家里用"这个约束下，B 档的每一样能力你都不需要，而它带来的失败模式全都要你承担 | |

### 2.3 一句话结论

> **不做后端服务、不做数据库；做一个"有服务端校验的静态站"。** 服务端只干两件事：签发 Cookie、校验 Cookie。这两件事加起来不超过 150 行 TypeScript，且不需要任何第三方库。

## 3. 访问保护的实现方案对比与落地规格

### 3.1 三案对比（含 Edge / Node 差异的正确姿势）

先给结论：**选 b 案，且不写 Proxy/中间件。**

| 方案 | 运行位置与运行时 | 能力 | 致命问题 | 结论 |
|---|---|---|---|---|
| **a. 中间件（旧名 `middleware.ts`，16.x 起为 `proxy.ts`）** | 在渲染前单独执行，官方设计目标是"可被部署到 CDN 的快速跳转/重写" | 能读请求 Cookie、能重定向 | ①历史包袱：v15.5 之前中间件只能跑 Edge Runtime，`node:crypto` 不存在，HS256 校验只能靠 WebCrypto（`crypto.subtle`）；网上大量"middleware + node:crypto"示例在旧版本直接报错——你要的就是这个组合别给。②官方文档明确写：**"Proxy 是让你在没有别的办法时才使用的手段"**，且不要依赖共享模块或全局变量，Cookie 只能做粗筛 | **不采用**（除非将来要拦未登录的静态资源请求） |
| **b. 根 layout / 路由组内 `cookies()` + 服务端校验（Node Runtime）** | React Server Component，跑在 Node.js 进程里；Next 16 Proxy 也默认 Node 运行时不代表 layout 不是，layout 天然就是 Node | 完整 `node:crypto`（`createHmac` / `timingSafeEqual` / `scrypt`）、可 `redirect()`、可读环境变量 | 每个受保护页面渲染前都做一次校验（微秒级，忽略不计） | **采用** |
| **c. 第三方库（next-auth / Auth.js、jose）** | 取决于库 | 开箱的提供方登录、会话表、CSRF token | ①这些库的设计目标是"多用户 + 多种 OAuth 提供方"，你的需求是**一个密码**；②会引入自己的 Cookie 格式、自己的迁移、自己的破坏性大版本升级（Auth.js v5 迁移就是活例）；③`jose` 单独用是合理的轻量选择，但它带来的只是"我已经会写的 20 行 HMAC" | **不采用**（`jose` 属于"可接受但没必要"） |

> **版本事实（已核）**：`middleware` 文件约定自 **v16.0.0** 起弃用并更名为 `proxy`，且 **Proxy 默认使用 Node.js 运行时**（v13.1 起有 advanced flags，v15.2 实验性、v15.5 稳定支持 Node 运行时）。所以"Edge 下没有 `node:crypto`"这个坑在 v16 新写法里已被官方绕开——但**你我不需要踩这个坑，因为 b 案根本不写这个文件**。如果未来要加，迁移命令是 `npx @next/codemod@canary middleware-to-proxy .`。

### 3.2 推荐结构（可执行）

**路由与文件职责**

```
src/
  app/
    login/page.tsx              # 公开：登录表单（<form action="/api/auth/login" method="post">）
    (hub)/
      layout.tsx                # 唯一鉴权闸门：await cookies() → 校验 → 不通过 redirect('/login')
      page.tsx                  # 主界面：搜索 / 卡片 / 收藏 / 最近使用
    api/auth/login/route.ts     # POST：限流 → 校验密码哈希 → Set-Cookie
    api/auth/logout/route.ts    # POST：清 Cookie（不接受 GET，见 §3.7）
  lib/auth/session.ts           # 'server-only'：HMAC 签发/校验、时序安全比较
  lib/auth/password.ts          # 'server-only'：scrypt 派生与校验
  lib/auth/rate-limit.ts        # 'server-only'：内存限流
  lib/auth/constants.ts         # Cookie 名、TTL、各开关
```

**要点：**

1. 受保护页面全部放进 `(hub)` 路由组，鉴权只写在 `(hub)/layout.tsx` **一处**。`/login` 在组外，天然不受影响。
2. `import 'server-only'` 放在 `lib/auth/*` 顶部，防止 HMAC 密钥或密码哈希被误 import 进客户端组件（构建期就报错，比 code review 可靠）。
3. **`cookies()` 在 Next 15.0.0 起是 async**，必须 `await cookies()`（v14 及更早是同步，网上老代码会误导你）。
4. 服务端组件**不能** `cookieStore.set()`；设置/删除 Cookie 只能在 Route Handler 或 Server Action 里做。因此登录/登出走 Route Handler。
5. **登录接口单独再校验一次**：Route Handler 是独立入口，layout 的闸门保护不到它（这条原则官方叫"每个 Server Function / Route Handler 内部都要重新鉴权"）。

```tsx
// src/app/(hub)/layout.tsx
import 'server-only'
import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'
import { verifySessionToken } from '@/lib/auth/session'
import { SESSION_COOKIE } from '@/lib/auth/constants'

export const dynamic = 'force-dynamic' // 会话相关，永远动态渲染

export default async function HubLayout({ children }: { children: React.ReactNode }) {
  const jar = await cookies()                       // ← 必须 await
  const ok = await verifySessionToken(jar.get(SESSION_COOKIE)?.value)
  if (!ok) redirect('/login')                       // 未登录：服务端直接 307，不闪内容
  return <>{children}</>
}
```

### 3.3 会话令牌签名结构

**格式**：`<payloadB64url>.<sigHex>`（两段，段内不含 `.`，便于 `split('.')`；不做嵌套解析，避免 JWT 那些 `alg: none` 类历史坑）

```
payloadB64url = base64url( JSON.stringify({ v:1, exp:<epochSeconds>, sub:"owner", rnd:"<含12字节随机数的base64url>" }) )
sigHex        = HMAC-SHA256(key = scrypt(SESSION_SECRET, "aihub.sig.v1", 32), data = payloadB64url) 的 hex
```

- **为什么不用 JWT**：JWT 的价值是跨系统互认，你只有一个系统。JWT 的代价是必须严格校验 `alg`、处理 `none`、处理 `kid`。自己写 20 行 HMAC，攻击面小得多。
- **为什么要 `rnd`**：让相同 `exp` 的两次登录产出不同令牌，避免"令牌看起来可预测"的直觉风险，也方便将来做黑名单（当前不做）。
- **`sub:"owner"` 的意义**：为将来"多用户"预留字段，但**当前不实现多用户**，校验时只接受 `sub === "owner"`，否则视为非法——防止以后有人瞎改 payload 就变成管理员。
- **不做服务端失效列表**：改密码即失效，理由见 §3.6。

```ts
// src/lib/auth/session.ts
import 'server-only'
import { createHmac, randomBytes, scryptSync, timingSafeEqual } from 'node:crypto'
import { SESSION_SECRET, SESSION_TTL_SECONDS } from './constants'

const KEY = scryptSync(SESSION_SECRET, 'aihub.sig.v1', 32) // 模块加载时派生一次

const b64url = (b: Buffer) => b.toString('base64url')

function sign(payloadB64: string): Buffer {
  return createHmac('sha256', KEY).update(payloadB64).digest() // 32 字节
}

export function issueSessionToken(now = Date.now()): string {
  const payload = {
    v: 1,
    sub: 'owner',
    exp: Math.floor(now / 1000) + SESSION_TTL_SECONDS,
    rnd: b64url(randomBytes(12)),
  }
  const p = b64url(Buffer.from(JSON.stringify(payload)))
  return `${p}.${sign(p).toString('hex')}`                                          // 64 个 hex 字符
}

export function verifySessionToken(token: string | undefined, now = Date.now()): boolean {
  if (!token) return false
  const i = token.indexOf('.')
  if (i <= 0 || i === token.length - 1) return false
  const p = token.slice(0, i)
  const macHex = token.slice(i + 1)
  if (!/^[0-9a-f]{64}$/.test(macHex)) return false        // 先做格式白名单，再比较

  // 时序安全比较：两边都是定长 Buffer（32 字节），不会抛 ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH
  const expected = sign(p)
  const given = Buffer.from(macHex, 'hex')
  if (!timingSafeEqual(expected, given)) return false

  try {
    const payload = JSON.parse(Buffer.from(p, 'base64url').toString('utf8')) as {
      v?: unknown; sub?: unknown; exp?: unknown
    }
    if (payload.v !== 1) return false
    if (payload.sub !== 'owner') return false
    if (typeof payload.exp !== 'number') return false
    if (payload.exp * 1000 <= now) return false            // 过期
    return true
  } catch {
    return false
  }
}
```

### 3.4 时序安全比较（为什么这么写，以及常见错误）

| 写法 | 是否时序安全 | 说明 |
|---|---|---|
| `a === b`（字符串） | ❌ | 短路比较，签名越像耗时越长，理论上可逐字节爆破 |
| `crypto.timingSafeEqual(a, b)` | ✅ | **要求两个 Buffer 长度相同**，否则抛 `ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH` |
| 先 `hash(x)` 再比较两个 hash | ✅ | 用于长度不可控的输入（如用户提交的令牌）。本项目固定 32 字节，不需要 |
| 先把 hex 转 Buffer 再比较 | ✅ | 本项目采用。**注意**：必须先校验 `^[0-9a-f]{64}$`，否则 `Buffer.from('zz','hex')` 会静默截断，长度不对就抛异常 |

**密码比较同理**：`scryptSync(input, salt, N, { N, r, p })` 得到定长 64 字节，再 `timingSafeEqual` 与存储哈希比较。绝不比较明文（明文长度不同，`timingSafeEqual` 会直接抛错，反而逼迫你写 `===`）。

```ts
// src/lib/auth/password.ts
import 'server-only'
import { randomBytes, scryptSync, timingSafeEqual } from 'node:crypto'

const N = 16384, r = 8, p = 1, KEYLEN = 64   // 约 16 MB 内存/次，本地自用足够

export function hashPassword(password: string): string {
  const salt = randomBytes(16)
  const h = scryptSync(password.normalize('NFKC'), salt, KEYLEN, { N, r, p })
  return `scrypt$${N}$${r}$${p}$${salt.toString('base64')}$${h.toString('base64')}`
}

export function verifyPassword(password: string, stored: string): boolean {
  const parts = stored.split('$')
  if (parts.length !== 6 || parts[0] !== 'scrypt') return false
  const [, n, rr, pp, saltB64, hashB64] = parts
  const salt = Buffer.from(saltB64, 'base64')
  const want = Buffer.from(hashB64, 'base64')
  const got = scryptSync(password.normalize('NFKC'), salt, want.length, {
    N: Number(n), r: Number(rr), p: Number(pp),
  })
  return got.length === want.length && timingSafeEqual(got, want)   // 防长度不等抛错
}
```

> 说明：`scrypt` 是 Node 内置、无需第三方依赖的密码派生函数。参数写进哈希串本身（`scrypt$N$r$p$salt$hash`），将来调参时旧哈希仍可校验，这是免费拿到的可升级性。

### 3.5 登录接口内存限流

**目标**：把在线爆破从"每秒任试"降到"每 15 分钟 5 次"。**已知局限（明说）**：进程内 Map，重启即清零，多实例不共享，也不防分布式爆破。单人内网自用可以接受；一旦暴露公网就该换 Redis 或直接在反向代理里做。

```ts
// src/lib/auth/rate-limit.ts
import 'server-only'

type Bucket = { fails: number; first: number; blockedUntil: number }
const buckets = new Map<string, Bucket>()

const WINDOW_MS = 10 * 60_000   // 统计窗口
const BLOCK_MS = 15 * 60_000    // 锁定
const MAX_FAILS = 5

// 反向代理后面必须信任 XFF，否则看到的都是 127.0.0.1（见 §8 部署注意事项）
export function clientKey(headers: Headers, trustProxy: boolean): string {
  if (trustProxy) {
    const xff = headers.get('x-forwarded-for')
    if (xff) return xff.split(',')[0]!.trim()
  }
  return headers.get('x-real-ip') ?? 'local'
}

export function checkLimit(key: string, now = Date.now()): { ok: boolean; retryAfterSec: number } {
  const b = buckets.get(key)
  if (!b) return { ok: true, retryAfterSec: 0 }
  if (b.blockedUntil > now) return { ok: false, retryAfterSec: Math.ceil((b.blockedUntil - now) / 1000) }
  if (now - b.first > WINDOW_MS) { buckets.delete(key); return { ok: true, retryAfterSec: 0 } }
  return { ok: true, retryAfterSec: 0 }
}

export function recordFailure(key: string, now = Date.now()): void {
  const b = buckets.get(key)
  if (!b || now - b.first > WINDOW_MS) { buckets.set(key, { fails: 1, first: now, blockedUntil: 0 }); return }
  b.fails += 1
  if (b.fails >= MAX_FAILS) b.blockedUntil = now + BLOCK_MS
}

export function clearFailures(key: string): void { buckets.delete(key) }

// 防内存泄漏：进程内定期清理（Next 的 instrumentation.ts register() 里挂一次即可）
setInterval(() => {
  const now = Date.now()
  for (const [k, b] of buckets) if (b.blockedUntil < now && now - b.first > WINDOW_MS) buckets.delete(k)
}, 5 * 60_000).unref?.()
```

**登录 Route Handler（含"恒定耗时"处理）**

```ts
// src/app/api/auth/login/route.ts
import 'server-only'
import { NextResponse } from 'next/server'
import { issueSessionToken } from '@/lib/auth/session'
import { verifyPassword } from '@/lib/auth/password'
import { checkLimit, recordFailure, clearFailures, clientKey } from '@/lib/auth/rate-limit'
import { SESSION_COOKIE, SESSION_TTL_SECONDS, TRUST_PROXY } from '@/lib/auth/constants'

export async function POST(req: Request) {
  const key = clientKey(req.headers, TRUST_PROXY)
  const lim = checkLimit(key)
  if (!lim.ok) {
    return NextResponse.json({ error: 'too_many_attempts' }, {
      status: 429, headers: { 'Retry-After': String(lim.retryAfterSec) },
    })
  }

  // 注意：这里用 formData 是为了 <form method="post"> 零 JS 也能登录；也可换 JSON
  const password = String((await req.formData()).get('password') ?? '')
  const stored = process.env.AUTH_PASSWORD_HASH ?? ''
  if (!stored) return NextResponse.json({ error: 'server_misconfigured' }, { status: 500 })

  if (!verifyPassword(password, stored)) {
    recordFailure(key)
    return NextResponse.redirect(new URL('/login?e=1', req.url), { status: 303 }) // 303 → 浏览器改 GET
  }
  clearFailures(key)

  const res = NextResponse.redirect(new URL('/', req.url), { status: 303 })
  res.cookies.set({
    name: SESSION_COOKIE,
    value: issueSessionToken(),
    httpOnly: true,                                    // ✅ 必备
    sameSite: 'lax',                                   // ✅ 见下表
    secure: process.env.COOKIE_SECURE !== '0',         // ⚠️ 纯 HTTP 内网必须显式设为 '0'
    path: '/',
    maxAge: SESSION_TTL_SECONDS,
  })
  return res
}
```

### 3.6 Cookie 属性表（逐项给理由）

| 属性 | 取值 | 理由 / 代价 |
|---|---|---|
| `httpOnly` | **true（不可协商）** | 杜绝 JS 读取，XSS 拿不到会话。代价：无法在客户端判断"是否已登录"——用一个不含秘密的 `aihub:ui` localStorage 标记做纯 UI 提示即可，**不要**把登录态判断建立在客户端 |
| `sameSite` | **lax** | 默认防护 CSRF（跨站 POST 不带 Cookie）。选 `lax` 而非 `strict` 的代价与收益：`strict` 会让你从微信/邮件里点链接进来时"看起来像被登出"（首次请求不带 Cookie），`lax` 对顶级导航放行、对跨站 POST 仍然拦截，正好符合登录表单场景 |
| `secure` | **HTTPS 下 true；局域网纯 HTTP 下必须为 false** | ⚠️ 这是本项目最容易踩的坑：`Secure` Cookie 在 `http://192.168.x.x` 下**不会**被浏览器存储，表现为"填了密码没反应、一直回登录页"。两个正解：①上 HTTPS（Tailscale / Caddy 内网证书 / `next dev --experimental-https`）→ `secure: true`；②纯内网 HTTP → `COOKIE_SECURE=0` 并接受令牌明文过局域网。**没有第三种正解。** |
| `maxAge` | **43200（12 小时）** | 自用站点，安全与麻烦的平衡点。想更懒可到 7 天（604800），代价是共用电脑上的窗口期变长。不需要 `expires`（`maxAge` 已足够） |
| `path` | **`/`** | 唯一路径就是根，收紧无收益还会漏掉 `/api` |
| `domain` | **不设** | 不设 = 仅当前主机，最紧。设了只会扩大作用域 |
| `priority` | 可选 `high` | 浏览器在淘汰 Cookie 时优先保留，纯锦上添花 |
| Cookie 名 | `aihub_session` | 不要叫 `session` / `token`（避免与其他本地服务的 Cookie 混淆） |

### 3.8 「忘记密码」与「改密码」的运维方式

先说设计取舍：**不实现"忘记密码"功能本身**，因为没有邮件/短信通道，任何"重置链接"都只能落在同一条链路上，等于给攻击者多一个入口。运维动作就是**改环境变量 + 重启**。

| 场景 | 操作 | 影响 | 备注 |
|---|---|---|---|
| 忘记密码 | 跑 `node scripts/hash-password.mjs` 生成新哈希 → 更新 `AUTH_PASSWORD_HASH` → 重启服务 | **所有会话立即失效**（因为签名密钥由密码哈希派生，见下） | 无需数据库、无需删除任何文件 |
| 主动改密码 | 同上（先跑 `scripts/verify-password.mjs` 确认当前密码，再改） | 同上 | 建议顺手也轮换 `SESSION_SECRET` |
| 手动踢掉所有会话（不改密码） | 轮换 `SESSION_SECRET` → 重启 | 所有会话立即失效 | 这是"远程登出"能力的最小实现 |
| 单设备登出 | 页面上的"登出"按钮 → `POST /api/auth/logout` → 清 Cookie | 只影响该浏览器 | **不要用 GET 做登出**：GET 会被链接预取、被邮件客户端扫链接触发；用 `POST` 表单按钮 |

**关键设计点——会话密钥派生自密码哈希，让"改密码 = 全端登出"免费成立：**

```ts
// src/lib/auth/constants.ts（节选）
import 'server-only'
import { scryptSync } from 'node:crypto'

const passwordHash = process.env.AUTH_PASSWORD_HASH ?? ''
if (!passwordHash) throw new Error('AUTH_PASSWORD_HASH 未设置')
if (!process.env.SESSION_SECRET) throw new Error('SESSION_SECRET 未设置')

export const SESSION_SECRET_SALT = 'aihub.sig.v1'
// 把「密码哈希」也揉进签名密钥：改密码后旧令牌的签名全部作废
export const SESSION_SECRET = `${process.env.SESSION_SECRET}|${passwordHash}`
export const SESSION_COOKIE = process.env.SESSION_COOKIE_NAME ?? 'aihub_session'
export const SESSION_TTL_SECONDS = Number(process.env.SESSION_TTL_SECONDS ?? 43200)
export const TRUST_PROXY = process.env.TRUST_PROXY === '1'
```

**两个别做的**：① 不要提供"仅凭原密码就能改密"的 HTTP 接口——那等于把改密能力挂在会话上，又多一个接口要保；单人站点直接改 `.env` 更安全、更省事。② 不要把密码哈希写进 git（`.env*` 必须在 `.gitignore` 里；只提交 `.env.example`）。

### 3.9 明确不做的部分

- ❌ 不写 `proxy.ts` / `middleware.ts`（官方建议非必要不用；也避开历史上 Edge 无 `node:crypto` 的坑）。
- ❌ 不做多用户 / 邀请码 / 注册。
- ❌ 不做 OAuth 登录（与"单人自用"无关，且引入第三方账号依赖）。
- ❌ 不做"记住我 30 天"以外的持久化选项（减少选项就是减少配置错误）。
- ⚠️ 若将来改成 `output: 'export'` 纯静态托管：**鉴权会完全失效**（静态导出不支持 Proxy 与动态渲染），此时必须改用 Cloudflare Access / 内网限制这类平台侧保护，不能靠应用代码。

## 4. 数据持久化：为什么 localStorage 足够

### 4.1 论证（先约束，再结论）

- 数据体积：6 个平台的 ID + 时间戳。收藏 ≤ 6 条、最近使用 ≤ 6 条，序列化后 **< 1 KB**，而 localStorage 单域上限通常为 5 MB 量级。【待核实：不同浏览器具体配额有差异】
- 访问模式：**只在当前这一个浏览器里读写**，无跨设备、无多人、无服务端查询、无聚合统计需求。
- 失败成本：清缓存丢收藏 → 用"导出/导入 JSON"兜底（10 行代码），比数据库备份便宜两个数量级。
- 引入数据库的代价：多一个常驻依赖、多一套迁移、多一处备份、多一类崩溃。**这三样都在给一个 < 1 KB 的数组服务。**

**结论：localStorage 足够。** 但有一条硬约束：**localStorage 永不存任何与"对话内容"有关的东西**（见 §4.5）。

### 4.2 TypeScript 类型定义


### 4.3 localStorage key 命名规范

| 规则 | 说明 |
|---|---|
| 统一前缀 `aihub:` | 避免与同域下其他工具冲突 |
| 单根键 `aihub:v1:state` | **只用一个键存状态**。多键会带来"部分写入成功"的不一致 |
| 键内带主版本 `v1` | 大版本不兼容时，新键与旧键可并存，便于回滚与清理 |
| 临时/一次性键用 `aihub:tmp:*` | 例如 `aihub:tmp:lastSearch`（会话结束即清） |
| 不存放秘密的 UI 标记：`aihub:ui:loggedIn` | 值为 `"1"`，仅用于首屏渲染样式，**任何安全判断都不读它** |
| 导出文件名：`aihub-backup-YYYYMMDD.json` | 便于按时间归档 |

### 4.4 版本迁移（schemaVersion）策略

三条铁律：**① 只前滚不后退；② 校验失败即重置为默认并能导出原始串；③ 迁移函数纯函数、可单测。**

```ts
// src/lib/storage/migrate.ts
import { CURRENT_SCHEMA_VERSION, type PersistedState } from './types'

export const DEFAULT_STATE: PersistedState = {
  schemaVersion: CURRENT_SCHEMA_VERSION,
  favorites: [],
  recents: [],
  settings: { theme: 'system', defaultOpenMode: 'list', showRecents: true },
  updatedAt: 0,
}

/** 每加一版，就在这里加一段；函数必须能从 v(n) 走到 v(n+1) */
const migrations: Record<number, (s: any) => any> = {
  // 1 → 2 的示例（当前还不存在）：
  // 1: (s) => ({ ...s, schemaVersion: 2, settings: { ...s.settings, newFlag: true } }),
}

export function migrate(raw: unknown): { state: PersistedState; from: number; reset: boolean } {
  if (!raw || typeof raw !== 'object') return { state: DEFAULT_STATE, from: 0, reset: true }
  let s = raw as any
  const from = typeof s.schemaVersion === 'number' ? s.schemaVersion : 0

  if (from > CURRENT_SCHEMA_VERSION) {
    // 用户可能在多个标签页开着新旧两个版本 → 不猜，保底重置（并保留原始串供导出）
    return { state: DEFAULT_STATE, from, reset: true }
  }
  for (let v = from; v < CURRENT_SCHEMA_VERSION; v++) {
    const fn = migrations[v]
    if (!fn) return { state: DEFAULT_STATE, from, reset: true }
    s = fn(s)
  }
  return { state: sanitize(s), from, reset: false }
}

/** 白名单式清洗：字段类型不对就丢该字段，绝不让脏数据进入渲染 */
export function sanitize(s: any): PersistedState {
  const known = new Set(['chatgpt', 'deepseek', 'gemini', 'qwen', 'kimi', 'zhipu'])
  const arr = (x: unknown) => (Array.isArray(x) ? x : [])
  return {
    schemaVersion: CURRENT_SCHEMA_VERSION,
    favorites: arr(s?.favorites)
      .filter((f: any) => known.has(f?.platformId) && Number.isFinite(f?.addedAt))
      .map((f: any) => ({ platformId: f.platformId, addedAt: f.addedAt, order: Number.isFinite(f.order) ? f.order : undefined }))
      .slice(0, 50),
    recents: arr(s?.recents)
      .filter((r: any) => known.has(r?.platformId) && Number.isFinite(r?.usedAt))
      .map((r: any) => ({ platformId: r.platformId, usedAt: r.usedAt, count: Number.isFinite(r.count) && r.count > 0 ? r.count : 1 }))
      .sort((a: any, b: any) => b.usedAt - a.usedAt)
      .slice(0, 6),                                   // 只有 6 个平台，上限锁死
    settings: {
      theme: ['system', 'light', 'dark'].includes(s?.settings?.theme) ? s.settings.theme : 'system',
      defaultOpenMode: ['open-one', 'list', 'copy-all'].includes(s?.settings?.defaultOpenMode)
        ? s.settings.defaultOpenMode : 'list',
      showRecents: typeof s?.settings?.showRecents === 'boolean' ? s.settings.showRecents : true,
    },
    updatedAt: Number.isFinite(s?.updatedAt) ? s.updatedAt : 0,
  }
}
```

```ts
// src/lib/storage/store.ts —— 客户端读写封装（注意：只能在 Client Component / effect 里调用）
'use client'
import { KEYS, CURRENT_SCHEMA_VERSION } from './keys'
import { DEFAULT_STATE, migrate, sanitize } from './migrate'
import type { PersistedState } from './types'

export function load(): PersistedState {
  try {
    const raw = localStorage.getItem(KEYS.state)
    if (!raw) return DEFAULT_STATE
    const { state, from, reset } = migrate(JSON.parse(raw))
    if (reset) {
      // 不要静默丢弃：留一份原始串，用户可从设置里导出并提 issue
      localStorage.setItem(`${KEYS.state}.corrupt.${Date.now()}`, raw)
      console.warn(`[aihub] 状态重置：schemaVersion ${from} → ${CURRENT_SCHEMA_VERSION}`)
    }
    return state
  } catch {
    return DEFAULT_STATE
  }
}

export function save(s: PersistedState): void {
  try {
    localStorage.setItem(KEYS.state, JSON.stringify({ ...sanitize(s), schemaVersion: CURRENT_SCHEMA_VERSION, updatedAt: Date.now() }))
  } catch (e) {
    // 配额满 / 隐私模式禁写：只告警，不影响跳转主流程
    console.warn('[aihub] 保存失败（隐私模式或配额）', e)
  }
}

/** 多标签页同步：另一个标签改了收藏，本标签实时更新 */
export function subscribe(fn: () => void): () => void {
  const h = (e: StorageEvent) => { if (e.key === KEYS.state) fn() }
  window.addEventListener('storage', h)
  return () => window.removeEventListener('storage', h)
}
```

**迁移的三条实践规则：**

1. 加字段 = 可选字段 + `sanitize` 给默认值，**不需要升版本**。
2. 改语义（例如 `recents` 从数组改成 map）= **必须升版本 + 写迁移函数**。
3. 升版本时同步更新"导出 JSON"里的 `schemaVersion`，让旧备份能被新代码识别（旧备份走迁移路径即可）。

### 4.5 隐私：不记录任何对话内容

| 允许写入 | 禁止写入 |
|---|---|
| 平台 ID、时间戳、使用次数、UI 偏好 | 提问文本、回答内容、对话链接、对话标题 |
| 搜索关键词？→ **只存最近一次，放在 `aihub:tmp:*`，且默认 30 秒后清**；建议直接不存 | 任何平台 Cookie / Token / 会话（**严禁**：那等于把你自己账号的钥匙交给这个站点） |
| 备份文件（用户手动导出，仅含上述 ID 与时间戳） | 设备指纹、IP、UA 快照、访问日志中的查询串 |

**两条容易被忽略的泄露点：**

1. **URL 参数**：如果以后做"搜索框直接跳到 ChatGPT 的 `?q=` 链接"，那个 q 会进入浏览器历史、Referer 头、以及目标平台的服务器日志。**当前需求不含此功能，明确不做。** 若将来要做，必须在 README 里写明"关键词会离开本机"。
2. **Referrer**：跳转到第三方平台时会带上 `Referer: http://你的站点/`。局域网 IP 会暴露给平台。默认无所谓，若想更严可以给外部链接加 `rel="noreferrer"`（代价：目标平台无法从来源判断，通常无影响）。

## 5. 「一键多开多个标签页」的浏览器限制真实情况

### 5.1 真实机制（先讲清规则，再谈方案）

1. **`window.open()` 必须在用户手势的同步调用栈里执行。** 一旦中间有 `await` / `setTimeout` / 网络往返，Transient User Activation 就失效，弹窗必被拦。**这条是铁律，所有"可靠"方案都建立在它之上。**
2. **弹窗拦截的阈值由浏览器决定，不是规范。** 规范没有规定"每次手势允许几个弹窗"；Chrome/Edge/Firefox 在缺少用户手势时一律拦截，而在有手势时允许的数量行为不一致（历史上 Chrome 对非手势弹窗"允许 1 个"的规则最常被引用，但**同一手势内多次 `window.open` 的实际通过数是实现细节**）。**【待核实——必须在你的目标浏览器上用 §6.2 的手工清单实测，不要相信任何博客给的数字。】**
3. **`noopener` 会让 `window.open` 返回 `null`**，此时你无法判断是"被拦截"还是"正常打开"。判断是否被拦只能看 `const w = window.open(...); if (!w) {...}`，而这又要求**不加 `noopener`**——这是安全与可检测性之间的真实取舍（建议：为了安全加 `noopener`，因此**放弃"逐个检测被拦后再补救"的复杂度**，直接走下面的推荐方案）。
4. **弹窗拦截 UI 因浏览器而异**：Chrome 地址栏右侧图标、Firefox 顶部横条。**UI 里必须写清提示文案**，否则用户只会觉得"这破站坏了"。

### 5.2 方案可靠性排序

| 排序 | 方案 | 可靠性 | 成本 | 失败模式 | 适用 |
|---|---|---|---|---|---|
| 1 | **TabList：同手势同步开 1 个 + 页面上渲染完整可点链接列表** | ★★★★★ 100% 可达（链接列表是普通 `<a>`） | 低 | 无。用户需多点几下（每次点击都是一个新手势） | ✅ **默认方案** |
| 2 | **TabCopy：复制全部链接到剪贴板 + 提示** | ★★★★☆ 高（受 `navigator.clipboard` 可用性影响） | 低 | 非安全上下文（纯 HTTP 且非 localhost）下 Clipboard API 不可用 → 降级为显示 `<textarea>` 让用户手动 Ctrl+C | ✅ 兜底方案 |
| 3 | **TabOpenSync：同手势连续 `window.open` N 次** | ★★☆☆☆ 不确定（取决于浏览器阈值，可能只开出 1 个） | 低 | 静默丢弃部分标签，用户以为都开了 | ⚠️ 仅作为"选项"，且必须同时显示链接列表 |
| 4 | **TabDelay：逐个延迟 200–500 ms 打开** | ★☆☆☆☆ 低（延迟破坏手势链 → 大概率被拦） | 低 | 几乎全被拦 | ❌ 不采用 |
| 5 | **生成链接列表页 / `data:` URL 页** | ★☆☆☆☆ 低（`data:` 顶层导航被浏览器阻断；Blob URL 需先创建再打开，且各浏览器对顶层 Blob 导航策略不同） | 中高 | 空白页 / 被拦 | ❌ 不采用【待核实：各浏览器 Blob 顶层导航策略差异较大】 |
| 6 | **Bookmarklet（书签小工具）** | ★★★★☆ 高（书签点击=用户手势，且 bookmarklet 生成的弹窗常被豁免） | 中（需用户手动拖书签，代码要压成一行） | 需用户一次性设置；CSP 严格时可能受限 | 🅿️ **P2 可选增强**，不做进 v1 |

### 5.3 推荐实现（含降级链）

**交互设计：**

```
[一键多开 ▾]
 ├─ 打开全部（最多 6 个） → 同手势开第 1 个 + 展开链接列表（默认）
 ├─ 复制全部链接         → 剪贴板（失败则弹出可复制的 textarea）
 └─ 依次打开（尽力）     → 同手势尝试 N 个，随后无条件展示链接列表
```

**代码骨架（关键点都标了）：**

```tsx
'use client'
import { useCallback, useState } from 'react'
import type { Platform } from '@/lib/storage/types'

export function useMultiOpen(platforms: Platform[]) {
  const [sheet, setSheet] = useState<Platform[] | null>(null)
  const [toast, setToast] = useState<string | null>(null)

  /** 默认：同步开第一个（必成功），其余走链接列表（100% 可达） */
  const openWithList = useCallback((list: Platform[]) => {
    const [first, ...rest] = list
    if (first) {
      // ⚠️ 同步调用，绝不能在 await / setTimeout 之后
      window.open(first.url, '_blank', 'noopener,noreferrer')
      void bumpRecent(first.id)
    }
    setSheet(rest)                       // 剩余的以真实 <a target="_blank"> 呈现
    if (rest.length) setToast('浏览器可能拦截连续弹窗：其余入口已列在下方，逐个点击即可')
  }, [])

  /** 复制全部链接：clipboard → textarea 降级 */
  const copyAll = useCallback(async (list: Platform[]) => {
    const text = list.map((p) => `${p.name}\t${p.url}`).join('\n')
    try {
      if (!navigator.clipboard || !window.isSecureContext) throw new Error('clipboard-unavailable')
      await navigator.clipboard.writeText(text)
      setToast(`已复制 ${list.length} 个链接，粘贴到地址栏或笔记即可`)
    } catch {
      setSheet(list)                     // 降级：把链接列出来，用户手动选/复制
      setToast('当前环境无法自动复制（非 HTTPS），请手动复制下方链接')
    }
  }, [])

  /** 尽力同步多开：只作为可选项，且永远附带链接列表 */
  const openBestEffort = useCallback((list: Platform[]) => {
    let opened = 0
    for (const p of list) {
      const w = window.open(p.url, '_blank')      // 不加 noopener 才能拿到返回值
      if (!w) break                               // 被拦即停，不再徒劳重试
      w.opener = null                             // 手动切断 opener 引用（替代 noopener 的安全效果）
      opened++
    }
    setSheet(list)
    setToast(opened < list.length
      ? `已打开 ${opened}/${list.length} 个，其余被浏览器弹窗拦截，请点击下方链接`
      : `已打开 ${opened} 个`)
  }, [])

  return { sheet, toast, setSheet, setToast, openWithList, copyAll, openBestEffort }
}
```

**链接列表渲染（这是可靠性的真正来源）：**

```tsx
{sheet && (
  <ul className="mt-3 space-y-1">
    {sheet.map((p) => (
      <li key={p.id}>
        <a href={p.url} target="_blank" rel="noopener noreferrer"
           className="text-blue-600 underline">
          {p.name} ↗
        </a>
      </li>
    ))}
    <li><button type="button" onClick={() => copyAll(sheet)}>复制以上链接</button></li>
  </ul>
)}
```

**必须写进 UI 的一句话**（否则用户会来问你为什么只开了一个）：

> 浏览器限制每次点击只能自动打开 1 个标签页；其余入口已列出，点开即可。首次使用时如看到拦截图标，请选择"始终允许本站弹出窗口"。

**风险提示（与平台条款相关）**：本方案本质是"替你点开 6 个官方网页的连接"，**不做批量请求、不模拟登录、不绕过任何验证**。但连续自动开多个标签在某些平台的风控视角下可能被视为异常批量访问，**这是 §10 风险清单里的一条，我明确不建议做"定时/循环自动打开"之类的增强**。

### 7.2 手工清单（必须人做，共 5 组）

**A. 功能**

1. 未登录访问 `/` → 被重定向到 `/login`；登录后回到主界面。
2. 搜索：输入 "kimi"/"智谱"/"qwen" 均能命中；无结果时给空状态文案。

4. 最近使用：点一个平台后刷新，该项排到最前；用满 6 个后不越界。
5. 一键多开三种模式各试一次，确认"链接列表"总能出现且每个链接可点通。
6. 登出后回首页 → 再次被拦。

**B. 兼容**

7. Chrome / Edge / Firefox 各跑一遍（**重点记录：同手势连续 `window.open` 的实际放行个数——这是 §5.1 标注的【待核实】项，用实测数字替换**）。
8. 手机浏览器（Safari iOS / Chrome Android）跑一遍：登录、`window.open`（移动端基本只允许 1 个）、复制链接（iOS 剪贴板需用户手势，已满足）。
9. 窗口宽度 375 / 768 / 1440 px 三档目测布局。

**C. 异常**

10. 密码输错 6 次 → 看到 429 / 锁定提示；等 15 分钟或重启服务恢复。
11. 手工把 localStorage 的 `aihub:v1:state` 改成 `"{{{"` → 刷新不白屏，数据重置且控制台有告警。
12. 浏览器开"阻止所有 Cookie" → 登录失败时有可读提示，而不是无限重定向（**检查点：不要出现重定向循环**）。
13. 删除 `.env.local` 后启动 → 进程报明确错误（不是静默允许所有人访问）。
14. 断网后点击平台 → 浏览器自身错误页（属于预期，可在 UI 加"需联网"文案）。

**D. 隐私**

15. DevTools → Application → Local Storage：**逐条确认没有对话文本、没有对话 URL、没有任何平台的 Cookie/Token**。
16. Network 面板：确认发往第三方的请求**只有**你点击后浏览器发起的顶层导航，本站没有任何后台埋点/统计请求。
17. 确认 URL 里没有 `?q=` 之类的关键词参数被带到第三方。

**E. 安全**

18. `httpOnly` 验证：控制台执行 `document.cookie` → **看不到 `aihub_session`**。
19. 篡改 Cookie：把 `aihub_session` 的值随便改一位 → 刷新被踢回登录。
20. CSRF 试探：从另一个站点/`curl` 向 `/api/auth/login` 发送跨站 POST → 因 `sameSite=lax` 不携带既有 Cookie（对本接口影响有限，但确认登出接口 `POST /api/auth/logout` 在跨站场景下无效）。
21. `secure` 验证：HTTPS 部署下确认 `Set-Cookie` 带 `Secure`；纯 HTTP 局域网部署下确认已显式关闭，并**在 README 里写明这是有意的降级**。

```powershell
npm run build

npm run start -- -H 0.0.0.0 -p 3000

# 2) 查本机在局域网里的 IPv4
ipconfig | Select-String 'IPv4'

# 3) 开防火墙入站规则（管理员 PowerShell，一次即可）
New-NetFirewallRule -DisplayName "AI Hub Nav 3000" -Direction Inbound `
  -Protocol TCP -LocalPort 3000 -Action Allow -Profile Private
```

**注意事项（按踩坑概率排序）：**

1. **只对 Private 配置文件放行**（`-Profile Private`）。别用 `-Profile Any`，那会在你连咖啡馆 Wi-Fi 时也把服务暴露到公共网络。若你的家庭网络被 Windows 识别为 Public，要么改网络配置为"专用网络"，要么显式加 `-Profile Public` 并清楚后果。
2. **`COOKIE_SECURE=0` 的代价要写进 README**：会话 Cookie 在局域网内明文传输，同网段的任何人都可能嗅探（现代家用 Wi-Fi 多为 WPA2/3 加密，风险有限，但访客网络与 IoT 网络通常能互通）。
3. **手机访问用 IP 而非机器名**：`http://192.168.1.23:3000`。用 `http://你的电脑名:3000` 时，若 DNS/NetBIOS 解析不稳会偶发打不开。
4. **`npm run start` 会随终端关闭而退出**。想常驻见 §8.3。
5. 想升级到 HTTPS（推荐，如果家里有访客设备）：
   - 方式 A：`npx next dev --experimental-https`（仅开发；它用 mkcert 生成本机信任的证书，但**手机不会信任**）。
   - 方式 B：用 Tailscale 之类的组网工具，走它自带的内网 HTTPS → 可把 `COOKIE_SECURE` 设回 `1`。
   - 方式 C：本地装 Caddy 反代 + 内网证书，然后设 `TRUST_PROXY=1` 让限流读到真实 IP。
   - ⚠️ 反向代理后面**必须**设 `TRUST_PROXY=1` 并确保代理传 `X-Forwarded-For`；否则限流看到的全是 `127.0.0.1`，一次失败会锁死所有人（也就是锁死你自己）。

### 8.2 方案二：Vercel

```powershell
npm i -g vercel        # 或 npx vercel
vercel login
vercel                 # 首次：预览部署，按提示回答（Framework 自动识别 Next.js）
# 在 Vercel 项目 → Settings → Environment Variables 配置：
#   SESSION_SECRET / AUTH_PASSWORD_HASH / SESSION_TTL_SECONDS / COOKIE_SECURE=1 / TRUST_PROXY=1

```

**注意事项：**

1. **必须设 `COOKIE_SECURE=1`**（Vercel 全站 HTTPS，不设会让 Cookie 在 HTTP 场景失效——虽然实际都是 HTTPS，但显式设置更清晰）。
2. **`TRUST_PROXY=1`**：Vercel 在代理后面，否则限流拿不到客户端 IP。
3. **环境变量改完必须重新部署**（`vercel --prod`）才生效；只在面板改动、不重部署，运行的仍是旧值。若用了 Server Actions 的闭包，注意 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 在多实例下需固定（官方文档说明，本项目若不用闭包可忽略）。
4. **域名会公开**。若不加访问保护就是"给全世界开的导航页"；本项目已有密码闸门，但请确认密码不是弱口令（§10）。
5. 部署目标若含**免费档额度限制**，本项目流量极小通常不触发；**具体额度与计费规则请以 Vercel 官方页面为准【待核实】**，我不在此引用任何价格。
6. 不要把 `.env.local` 提交到 git；Vercel 用面板变量，不用文件。

### 8.3 方案三：自有 Windows 机器常驻（三种方式）

**先做的准备**：`npm run build` 通过，`.env.local` 就位；把 `COOKIE_SECURE` 按是否有 HTTPS 设好。

**方式 3A：pm2（最省事）**

```powershell
npm i -g pm2 pm2-windows-startup
pm2 start npm --name ai-hub-nav -- run start -- -H 0.0.0.0 -p 3000
pm2 save
pm2-startup install          # 注册登录自启
pm2 logs ai-hub-nav          # 看日志
pm2 restart ai-hub-nav
```

- 注意：pm2 读取的是当前 shell 的环境变量；`.env.local` 由 Next 自己加载（`next start` 会读 `.env.production` / `.env.local`），**但 shell 级变量（如 `COOKIE_SECURE=0`）需要写进 `.env.local`**，否则 pm2 重启后丢失。
- 【待核实：pm2-windows-startup 在新版 Windows/Node 下的兼容性】。若 `pm2-startup install` 报错，直接用 3B。

**方式 3B：NSSM 注册为 Windows 服务（最稳）**

```powershell
# 下载 nssm 并解压到 C:\tools\nssm（来源与校验方式以官方发布页为准）
C:\tools\nssm\win64\nssm.exe install AIHubNav "C:\Program Files\nodejs\node.exe" "C:\path\to\ai-hub-nav\node_modules\next\dist\bin\next start -H 0.0.0.0 -p 3000"
C:\tools\nssm\win64\nssm.exe set AIHubNav AppDirectory "C:\path\to\ai-hub-nav"
C:\tools\nssm\win64\nssm.exe set AIHubNav AppStdout "C:\logs\aihub\out.log"
C:\tools\nssm\win64\nssm.exe set AIHubNav AppStderr "C:\logs\aihub\err.log"
C:\tools\nssm\win64\nssm.exe set AIHubNav AppRotateFiles 1
C:\tools\nssm\win64\nssm.exe set AIHubNav AppRotateBytes 10485760   # 10 MB 轮转
C:\tools\nssm\win64\nssm.exe set AIHubNav Start SERVICE_AUTO_START
C:\tools\nssm\win64\nssm.exe start AIHubNav
```

- 关键点：**用 `node.exe` 直接跑 `next` 的 bin，而不是 `npm.cmd`**（避免 npm 作为父进程带来的信号/退出码问题，服务停止时更干净）。
- 服务启动失败不会弹窗，一定去 `err.log` 看。最常见原因：`AppDirectory` 不对、环境变量没配、端口被占。
- 服务账户默认 `LocalSystem`：它有权限读 `.env.local`，但也意味着密钥落在系统账户可读范围。单人机器可接受；若要收紧，改用专用低权限账户并把项目目录 ACL 限定给该账户。

**方式 3C：任务计划程序（不想装任何东西时）**

```powershell
$action  = New-ScheduledTaskAction -Execute "C:\Program Files\nodejs\node.exe" `
  -Argument "node_modules\next\dist\bin\next start -H 0.0.0.0 -p 3000" `
  -WorkingDirectory "C:\path\to\ai-hub-nav"
$trigger = New-ScheduledTaskTrigger -AtStartup
$trigger.Delay = 'PT30S'                          # 等网络就绪
$set     = New-ScheduledTaskSettingsSet -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 1) `
  -ExecutionTimeLimit ([TimeSpan]::Zero) -StartWhenAvailable
Register-ScheduledTask -TaskName "AIHubNav" -Action $action -Trigger $trigger -Settings $set -RunLevel Highest
```

- 关键点：`-ExecutionTimeLimit` 必须设为 0（无限），否则默认 3 天后任务会被强杀——**这是任务计划方式最经典的坑**。
- `-AtStartup` 而非 `-AtLogOn`：后者要求你登录后才会启动。
- 该方式的日志需要自己重定向（`*>> C:\logs\aihub\out.log`），且不会自动轮转。

**三方案的取舍**：pm2 最方便但依赖其 Windows 自启组件；NSSM 最稳、日志/轮转/自动重启齐全，代价是引入一个第三方小工具；任务计划零依赖，但日志与轮转要自己搭。**推荐：长期跑用 NSSM；只是偶尔开着用就 pm2。**

### 8.4 HTTPS 提醒（三条硬话）

1. **有 `Secure` Cookie 就必须有 HTTPS**，否则浏览器不存 Cookie，表现为"登录无反应"。
2. **纯 HTTP 内网就关 `Secure`**，并接受会话令牌明文过网；**这是有意的取舍，必须写在 README 里，不能默默这么做**。
3. **不要把家用机器直接暴露到公网**（不做端口映射、不做 DMZ）。要外网访问，用 Tailscale / Cloudflare Tunnel 之类只暴露认证后通道的方案，且**必须**同时把 `TRUST_PROXY` 与 `ALLOWED_ORIGINS` 配对设置好。

## 9. 我行使否决权的部分（不在你的选择范围内）

| 项 | 否决理由 |
|---|---|
| 把会话令牌放 `localStorage` 或非 `httpOnly` Cookie | 等于给 XSS 提供一键登录跳板；且校验密钥会进浏览器 bundle |
| 提交 `.env` / 明文密码进 git | 密钥一旦入库就永久泄露（历史记录里删不干净） |
| 为"多开"写任何形式的循环/定时自动打开逻辑 | 会被平台视为异常批量访问，触碰风控与条款红线 |
| 跳过 §7.2 的 C/E 两组（隐私与安全）手工验证 | 这两组各 5 分钟，是刹车不是功能 |
| 用 `GET /api/auth/logout` | 会被链接预取、被扫描器触发，属于可被强制登出的小 CSRF |
| 在客户端代码里 import `lib/auth/*` | 会泄露 HMAC 密钥与密码哈希（用 `server-only` 在构建期硬拦） |

### 「暂不建议做」清单（现在做，得不偿失）

1. **多用户 / 邀请码 / 注册** —— 需求不存在，却引入账号体系与更复杂的数据面。
2. **数据库（SQLite / Postgres）** —— 除非出现"多设备同步收藏"的真实需求。
3. **OAuth / 第三方登录（next-auth）** —— 给一个密码的需求装一整套认证框架，升级利息高。
4. **自动打开多个标签的"增强"（定时、循环、随机延迟）** —— 触碰平台风控与条款边界，明确不做。
5. **任何形式的爬取官方页面标题/图标/可用性探测** —— 违反你已锁定的约束，且会带来 CORS、反爬、条款三重麻烦。图标用本地 SVG 或纯文字色块。
6. **埋点/统计（Vercel Analytics、Umami 等）** —— 与"隐私优先、不记录行为"自相矛盾；单人自用也看不出你想看的指标。
7. **`output: 'export'` 纯静态托管** —— 会直接废掉鉴权（静态导出不支持 Proxy 与请求期 Cookie），除非改用平台侧访问控制。
8. **国际化 / 主题系统 / 拖拽排序 v1 就上** —— 6 个卡片不需要。拖拽排序可以 P2。

## 12. ADR（架构决策记录）

### ADR-001：采用 Next.js 16.4 + App Router，不启用 Cache Components

- 日期 / 决策人 / 状态：2026-10-09 / CTO / **提议**
- **当时的约束**：项目为单人自用导航站；团队成员 1 人（熟悉 React/TS，无需培训）；在招市场供给不适用；数据量 < 1 KB，全部在浏览器本地；预算 = 两个晚上；不可动承诺 = 不接 API、不爬取、只做跳转
- 备选方案与淘汰理由：
  - **纯静态 HTML + 少量 JS**：最快，但会失去类型安全与组件复用，且以后加设置页要重构 → 淘汰
  - **Vite + React SPA**：无 SSR 需求，但访问保护（服务端写 `httpOnly` Cookie）需要另起一个后端 → 淘汰
  - **Next.js 15.x（更保守）**：教程更多，但已不是当前 stable，且未来升级路径更长 → 淘汰
  - **Next.js 16.4 + Cache Components**：新缓存模型对静态导航站零收益，且 `cookies()` 与 prerender 的交互会制造额外构建复杂度 → 淘汰
- 决定与已知代价：采用 Next.js 16.4.x + App Router（TS/Tailwind）。已知代价：新版文件约定（`middleware` → `proxy`）与网上多数教程不一致，抄代码需自行鉴别；Next 17 的缓存模型变更是一笔未来本金
- 复审触发条件：Next 17 stable 发布；或本项目需要真正的服务端个性化渲染

### ADR-002：不做数据库，用环境变量 + 无状态 HMAC 会话

- 日期 / 决策人 / 状态：2026-10-09 / CTO / **提议**
- **当时的约束**：单人自用；单浏览器数据；数据量 < 1 KB；无多用户、无跨设备同步需求；无可用的邮件/短信通道
- 备选方案与淘汰理由：
  - **SQLite / Postgres 存会话与收藏**：引入备份、迁移、崩溃恢复三类失败模式，换来的能力当前都用不上 → 淘汰
  - **令牌放 localStorage（零服务端）**：XSS 可直接窃取会话，且签名密钥会进浏览器 bundle → **否决**（安全底线）
  - **next-auth / Auth.js**：为"一个密码"引入整套认证框架与其大版本升级 → 淘汰
  - **`jose`**：可行，但只省下约 20 行 HMAC 代码，却多一个依赖 → 淘汰（保留为将来需要 JWT 互认时的选项）
- 决定与已知代价：密码哈希与签名密钥存环境变量；会话令牌为 `base64url(payload).hmacHex` 的自签格式；改密码即全端登出。已知代价：换设备不同步收藏（用手工 JSON 导出兜底）；无法单独踢掉某一台设备
- 复审触发条件：出现多设备同步的真实需求；或站点需要暴露到公网（届时限流与失效粒度需重新评估）

### ADR-003：访问保护放在根 layout（Node Runtime），不写 Proxy/中间件

- 日期 / 决策人 / 状态：2026-10-09 / CTO / **提议**
- **当时的约束**：Next.js 16.4（`middleware` 已弃用更名 `proxy`）；团队 1 人；历史上有"Edge Runtime 无 `node:crypto`"的知识陷阱；本站只有 1 个受保护页面、0 个需拦截的静态资源
- 备选方案与淘汰理由：
  - **`proxy.ts` / `middleware.ts` 做校验**：官方文档明确建议"非必要不用"；历史上（v15.5 之前）只能跑 Edge Runtime，`node:crypto` 不可用，网上大量示例在旧版本直接报错；本站没有需要拦截静态资源的场景 → 淘汰
  - **第三方会话库**：见 ADR-002 → 淘汰
  - **`(hub)/layout.tsx` + `await cookies()` + `node:crypto`**：完整 Node API、单一闸门、构建期可用 `server-only` 保护密钥 → **采用**
- 决定与已知代价：鉴权只在 `src/app/(hub)/layout.tsx` 一处；登录/登出走 Route Handler。已知代价：若将来要为静态资源（图片/PDF）加访问控制，layout 方案覆盖不到，需回到 Proxy 或反向代理层
- 复审触发条件：需要保护非页面资源；或需要在渲染前（早于 RSC 流式响应）做重定向判断

### ADR-004：一键多开以"同手势开 1 个 + 链接列表"为默认，不做延迟连开

- 日期 / 决策人 / 状态：2026-10-09 / CTO / **提议**
- **当时的约束**：浏览器弹窗拦截阈值由实现决定、无规范保证【待核实：需实测】；`window.open` 必须在用户手势的同步栈内；不加 `noopener` 才能检测拦截，但与安全取向冲突
- 备选方案与淘汰理由：
  - **逐个延迟打开（200–500 ms）**：延迟破坏手势链，几乎必被拦 → 淘汰
  - **生成链接列表页 / `data:` URL 中间页**：`data:` 顶层导航被阻断，Blob 顶层导航策略各浏览器不一 → 淘汰
  - **纯 `window.open` × N**：可能只开出 1 个且静默失败，用户体验是"这站坏了" → 降级为可选项
  - **同手势开 1 个 + 渲染真实 `<a>` 链接列表 + 复制全部链接兜底**：100% 可达，失败模式为零 → **采用**
- 决定与已知代价：默认走链接列表；"依次打开（尽力）"作为可选项且永远附带列表。已知代价：多一次点击；`rel="noopener"` 使"检测是否被拦"的能力被放弃（选择安全）
- 复审触发条件：实测发现目标浏览器稳定允许同手势开 ≥3 个标签页（届时可把"依次打开"提为默认）；或用户明确要求 Bookmarklet 方案
